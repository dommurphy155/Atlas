  2. Atlas → Ollama mapping (every file)

  Atlas file: ~/atlas/proxy/config.py

  Ollama equivalent(s): envconfig/config.go + api/types.go + types/model/

  Why / responsibility: Atlas has one config.py (752 lines) that mixes env

  parsing, path resolution, provider registry, model defaults, key lifecycle,

  and per-provider switch. Ollama splits this into 4 places: envconfig/ (env

  accessors + EnvVar registry with descriptions), api/types.go

  (request/response types), types/model/

  (Capability/ConfigV2/GenerationDefaults), and internal/modelref/

  (:cloud/:local parsing).

  ────────────────────────────────────────

  Atlas file: ~/atlas/proxy/keypool.py

  Ollama equivalent(s): server/sched.go + llm/server.go (LlamaServer interface)

  +

  keypool aspect of auth/auth.go

  Why / responsibility: Atlas's key pool = atomic round-robin with

  cooldown/suspend, partial-sticky + full-sticky modes. Ollama's analog isn't

  "key pool" — it's model pool: Scheduler (1,460 lines in server/sched.go) maps

   LlmRequest → loaded runnerRef with the same per-model concurrency, OOM

  eviction, sticky-loaded-vs-evict semantics, and recovery. The actual

  interface boundary (Atlas's KeyPool.next_key()) is Ollama's LlamaServer

  interface in llm/server.go:59 (Completion, Chat, ApplyChatTemplate,

  Embedding, Tokenize, …). OAuth-key rotation maps to auth/auth.go (SSH ed25519

   signing for ollama.com).

  ────────────────────────────────────────

  Atlas file: ~/atlas/proxy/logger.py

  Ollama equivalent(s): logutil/logutil.go + server/inference_request_log.go +

  format/bytes.go format/time.go

  Why / responsibility: Atlas has logger.py (root logger setup, JSON formatter)

  +

  prettylog.py (request lifecycle trace, TTFT, chunks, key health). Ollama uses

   stdlib log/slog with a thin logutil.NewLogger() wrapper that adds TRACE

  level + source-path redaction. Per-request debug capture is a separate opt-in

   (inference_request_log.go, gated by OLLAMA_DEBUG_LOG_REQUESTS) — writes

  curl-replayable request bodies to a tempdir. There's no Atlas-style

  TTFT/chunk counter middleware; metrics come from the LLM server itself

  (llamaServerTimings).

  ────────────────────────────────────────

  Atlas file: ~/atlas/proxy/main.py

  Ollama equivalent(s): cmd/cmd.go (RunServer) + server/routes.go (Serve)

  Why / responsibility: Atlas's main.py = FastAPI app + lifespan + periodic key

  reload. Ollama's main.go → cmd.NewCLI().ExecuteContext() → RunServer (line

  2015) → server.Serve(ln) (line 1963). The Serve function in routes.go does:

  set up slog → fix blobs → prune unused layers → build Server{} with

  modelCaches and sched → start sched.Run(ctx) → register webp decoder →

  enumerate GPUs → set VRAM-tier default num_ctx → srvr.Serve(ln). Same

  responsibilities as Atlas's lifespan, but spread across cobra + Serve +

  per-init helper functions.

  ────────────────────────────────────────

  Atlas file: ~/atlas/proxy/prettylog.py

  Ollama equivalent(s): format/bytes.go + format/time.go + per-request model

  logs

  in routes.go

  Why / responsibility: Atlas's prettylog is a custom formatter + RequestTrace

  (TTFT, in-flight, throughput) + keys_health() rendering. Ollama has no

  equivalent middleware. Status reporting is inline in routes.go handlers via

  slog.Info("key health",  ...) patterns. Atlas's RequestTrace is a real piece

  of value Ollama lacks — Ollama's metrics come from the LLM server's own

  response (EvalDuration, PromptEvalCount in api.Metrics).

  ────────────────────────────────────────

  Atlas file: ~/atlas/proxy/proxy.py

  Ollama equivalent(s): llm/llama_server.go + llm/server.go + server/sched.go +

  server/cloud_proxy.go + internal/proxy/codex_desktop.go

  Why / responsibility: Atlas's proxy.py is 1,119 lines: ProxyCore.forward()

  with

  retry loop, model override, mid-stream SSE error classification, free-model

  semaphore, response size cap. Ollama has no single "ProxyCore" — the

  equivalent work is scattered: (a) llm/llama_server.go is the subprocess

  management + HTTP client to llama-server (2,880 lines, includes the

  llamaServerRunner struct that wraps exec.Command and reads NDJSON streaming

  responses); (b) server/sched.go is the load balancer that picks a loaded

  runner; (c) server/cloud_proxy.go is the cloud pass-through (1,034 lines);

  (d) internal/proxy/codex_desktop.go (690 lines) and claude_desktop.go (972

  lines) are reverse-proxies for Codex Desktop / Claude Desktop that route to

  ollama.com. Atlas's single file = Ollama's 5+ files.

  ────────────────────────────────────────

  Atlas file: ~/atlas/proxy/routes.py

  Ollama equivalent(s): server/routes.go + openai/openai.go +

  openai/responses.go

  + anthropic/anthropic.go + middleware/openai.go + middleware/anthropic.go

  Why / responsibility: Atlas's routes.py (904 lines) is FastAPI handlers for

  /v1/chat/completions, /v1/messages, /v1/responses, /v1/models, /healthz, plus

   Codex-specific apply_patch logic. Ollama splits this cleanly:

  server/routes.go (2,390 lines) is only the gin route registration +  handler 

  entry points; all wire-format types live in  openai/ and anthropic/ packages;

   all inbound-format →  internal-type translation lives in middleware/. The

  GenerateRoutes() function (line 1846) reads as a clean table of contents of

  every endpoint. Atlas inlines the conversion logic inside handlers; Ollama

  splits them.

  ────────────────────────────────────────

  Atlas file: ~/atlas/proxy/system_prompt.py

  Ollama equivalent(s): template/template.go + server/prompt.go + Modelfile 

  SYSTEM directive in parser/parser.go + tools/tools.go + thinking/parser.go

  Why / responsibility: Atlas's system_prompt.py does two things: (a) additive

  system-prompt override injection, (b) Anthropic "billing-header" stripping.

  Ollama's analog is fundamentally different — there's no "system prompt

  injection at the proxy" because the system prompt is part  of the model 

  definition (Modelfile's SYSTEM directive, parsed in parser/parser.go,

  rendered by template/template.go, called via chatPrompt() in

  server/prompt.go). Per-model tool/thinking tag parsing lives in dedicated

  parsers (tools/, thinking/, harmony/), not in a single prompt file. There is 

  no analog of  Atlas's "strip harness" mode in Ollama — the model sees

  whatever the model author wrote in the Modelfile.

  ────────────────────────────────────────

  Atlas file: ~/atlas/proxy/translation.py

  Ollama equivalent(s): openai/openai.go (FromChatRequest, ToChatCompletion,

  ToStreamChunks) + openai/responses.go (ToResponse, ResponsesStreamConverter)

  + anthropic/anthropic.go (FromMessagesRequest, ToMessagesResponse,

  StreamConverter) + thinking/parser.go + tools/tools.go +

  harmony/harmonyparser.go + middleware/openai.go (ChatMiddleware,

  ResponsesMiddleware)

  Why / responsibility: Atlas's translation.py is 1,724 lines doing

  OpenAI↔Anthropic conversion, reasoning/thinking normalization, tool format

  adaptation, context-window trimming, and Codex custom-tool handling. Ollama

  splits this into: (a) openai/ and anthropic/ packages = pure wire-format

  types and one-way conversion functions (FromChatRequest returns

  api.ChatRequest, ToChatCompletion returns the OpenAI-shaped response); (b)

  middleware/openai.go and middleware/anthropic.go = the gin handler-shim that

  does the inbound parse → internal-type conversion → request body rewrite,

  then post-processes the streamed response (the

  BaseWriter/ChatWriter/ResponsesWriter types in middleware/openai.go:26-200);

  (c) thinking/, tools/, harmony/ = streaming parsers that turn token streams

  into structured Thinking + ToolCall fields. Atlas combines what Ollama splits

   into 6+ files.

  ────────────────────────────────────────

  Atlas file: ~/atlas/proxy/utils.py

  Ollama equivalent(s): api/client.go (Go SDK) + format/bytes.go +

  format/format.go + format/time.go + internal/orderedmap/ + internal/modelref/

  Why / responsibility: Atlas's utils.py is 52 lines: orjson wrappers,

  request_id, is_openai_done_frame. Ollama has no analog to utils.py as a

  grab-bag. JSON is encoding/json (stdlib). api/client.go is the SDK the CLI

  uses to talk to its own server — analogous to Atlas's lack of one (Atlas has

  no client SDK; Claude Code is the client). format/ is small focused helpers

  (HumanBytes2, duration formatting). internal/orderedmap/ preserves key order

  in JSON round-trips.

  Files that combine what Atlas splits

  - server/routes.go is 2,390 lines and contains: route registration, every

    handler (GenerateHandler, ChatHandler, EmbedHandler, ShowHandler,

    ListHandler, PullHandler, PushHandler, DeleteHandler, CreateHandler,

    StatusHandler, PsHandler, WhoamiHandler, SignoutHandler, web search/fetch

    handlers, model recommendations), all error helpers

    (writeModelRefParseError, handleScheduleError), and the cross-platform

    Serve() entry. Atlas's equivalent (routes.py + parts of proxy.py + parts of

    translation.py + parts of main.py) is split into 5 files; Ollama collapses

    them into one.

  Files that split what Atlas combines

  - Atlas's translation.py (1,724 lines) = Ollama's openai/ + anthropic/ + 

    middleware/ + thinking/ + tools/ + harmony/ = 6+ files / ~5,000 lines.

    Ollama cleanly separates the inbound-conversion (FromChatRequest) from the

    outbound-conversion (ToChatCompletion).

  - Atlas's proxy.py + keypool.py (1,573 lines) = Ollama's llm/server.go + 

    llm/llama_server.go + server/sched.go + server/cloud_proxy.go = ~6,000 

    lines. Ollama cleanly separates the LLM subprocess wrapper (llm/) from the

    scheduler (server/sched.go) from the cloud passthrough

    (server/cloud_proxy.go).

  - Atlas's config.py (752 lines) = Ollama's envconfig/ + api/types.go + 

    types/model/ + internal/modelref/. Ollama has separate types from config

    from environment access.

  3. Reverse: Ollama components Atlas doesn't have

  Ollama component: Scheduler

  File(s): server/sched.go (1,460 lines)

  Responsibility: Maps LlmRequest → runnerRef, manages model loading/unloading,

  OOM eviction, auto-reduce num_ctx on load failure

  (reduceAutoNumCtxForLoadOOM), GPU layer splitting. This is  Ollama's most 

  important piece Atlas has no analog of.

  Atlas equivalent / missing: Atlas has nothing here — its "load" is "send an

  HTTP request." If Atlas ever needed to hold a model in memory, it would need

  this.

  ────────────────────────────────────────

  Ollama component: LlamaServer interface

  File(s): llm/server.go:59-78

  Responsibility: Pluggable inference backend abstraction. Defines Completion(),

  Chat(), ApplyChatTemplate(), Embedding(), Tokenize(), Detokenize(), Load(),

  Close(), MemorySize(). Multiple implementations possible (llama.cpp

  subprocess, MLX).

  Atlas equivalent / missing: Atlas has a hard-coded httpx.AsyncClient. No

  interface. If Atlas ever added a second backend, it would need this.

  ────────────────────────────────────────

  Ollama component: llamaServerRunner

  File(s): llm/llama_server.go (2,880 lines)

  Responsibility: The concrete LlamaServer impl that spawns

  exec.Command("llama-server", ...) and reads its NDJSON streaming output.

  Builds CLI flags, handles library path env, GPU detection, mmap.

  Atlas equivalent / missing: Atlas does the equivalent inline in

  _open_upstream_stream() and _stream_forward(). No separate file.

  ────────────────────────────────────────

  Ollama component: Model struct + Capabilities()

  File(s): server/images.go:65-88

  Responsibility: Every model is a typed object: Config, Template,

  Capabilities(), IsMLX(), generationDefaultsFromGGUF(). Capabilities are

  detected from GGUF metadata + template inspection (tool support, thinking

  support, vision).

  Atlas equivalent / missing: Atlas has ProviderConfig (just URL + key prefix +

  model name) — no capability detection, no template metadata, no model

  introspection.

  ────────────────────────────────────────

  Ollama component: ModelResolver / parseAndValidateModelRef

  File(s): server/model_resolver.go + internal/modelref/

  Responsibility: Parses model:tag strings, handles :cloud / :local suffix

  routing, validates names against the manifest store.

  Atlas equivalent / missing: Atlas has no model resolver — it's a proxy to

  external APIs, so the client picks the model name.

  ────────────────────────────────────────

  Ollama component: create.go (model creation pipeline)

  File(s): server/create.go (1,500 lines)

  Responsibility: Pulls a model, parses its GGUF/safetensors, quantizes, embeds

  metadata, writes blobs.

  Atlas equivalent / missing: Atlas has nothing — it never creates or stores

  models.

  ────────────────────────────────────────

  Ollama component: Model caches

  File(s): server/model_list_cache.go, model_show_cache.go,

  model_inference_cache.go

  Responsibility: Local caches to make /api/tags, /api/show, inference lookups

  O(1) — SWR-style with TTL.

  Atlas equivalent / missing: Atlas has no model cache.

  ────────────────────────────────────────

  Ollama component: parsers/ (Modelfile parser)

  File(s): parser/parser.go (560 lines)

  Responsibility: Parses FROM, PARAMETER, TEMPLATE, SYSTEM, LICENSE, ADAPTER

  etc.

  from a Modelfile into structured commands.

  Atlas equivalent / missing: Atlas has no model-definition language.

  ────────────────────────────────────────

  Ollama component: template/ (Go templates)

  File(s): template/template.go (1,000+ lines + 30+ model-specific templates)

  Responsibility: Renders prompts using Go's text/template for 30+ chat formats

  (chatml, llama3, mistral, vicuna, etc.).

  Atlas equivalent / missing: Atlas has no template engine — it forwards raw

  messages to OpenRouter, which does the templating.

  ────────────────────────────────────────

  Ollama component: tokenizer/ (BPE/SP/WordPiece)

  File(s): tokenizer/ (4 files)

  Responsibility: Local tokenization.

  Atlas equivalent / missing: Atlas has no tokenizer.

  ────────────────────────────────────────

  Ollama component: convert/ (architecture-specific safetensors → GGUF)

  File(s): convert/convert_*.go (60+ files)

  Responsibility: Per-architecture conversion for 30+ model families (Gemma 3/4,

  Llama 4, Mistral, Qwen 3, DeepSeek, etc.).

  Atlas equivalent / missing: Atlas doesn't do any of this.

  ────────────────────────────────────────

  Ollama component: x/mlxrunner/ (alternative inference engine)

  File(s): x/mlxrunner/runner.go + server.go

  Responsibility: Pure-Go alternative to llama.cpp subprocess for Apple Silicon.

  Started as a separate executable (cmd/runner/main.go → runner.Execute() →

  mlxrunner.Execute()).

  Atlas equivalent / missing: Atlas has no second backend.

  ────────────────────────────────────────

  Ollama component: harmony/ (GPT-OSS parser)

  File(s): harmony/harmonyparser.go (17 lines) + integration

  Responsibility: Streaming parser for OpenAI's harmony response format.

  Atlas equivalent / missing: Atlas has no parser; it relies on upstream

  OpenRouter.

  ────────────────────────────────────────

  Ollama component: tools/ (tool-call streaming parser)

  File(s): tools/tools.go (500 lines) + tools/template.go (1,500 lines)

  Responsibility: Streaming JSON tool-call parser with templated output.

  Atlas equivalent / missing: Atlas's tool handling is in translation.py; no

  streaming parser.

  ────────────────────────────────────────

  Ollama component: thinking/ (thinking-tag streaming parser)

  File(s): thinking/parser.go (500 lines) + thinking/template.go (1,000 lines)

  Responsibility: Splits a token stream into thinking + visible content.

  Atlas equivalent / missing: Atlas's thinking handling is in translation.py; no

  streaming parser.

  ────────────────────────────────────────

  Ollama component: internal/proxy/ (Codex Desktop, Claude Desktop)

  File(s): internal/proxy/codex_desktop.go (690) + codex_desktop_normalize.go

  (455) + claude_desktop.go (972) + claude_desktop_models.go (474)

  Responsibility: A full reverse-proxy that sits between Codex/Claude Desktop

  and

  ollama.com, normalizing requests, adding zstd decoding, rewriting model

  names. ~3,200 lines of code, ~6,000 lines of tests.

  Atlas equivalent / missing: Atlas has Codex handling in routes.py (~250 lines,

  no Claude Desktop support). Ollama treats this as a first-class concern.

  ────────────────────────────────────────

  Ollama component: convert/sentencepiece/ (proto-generated Go)

  File(s): convert/sentencepiece/ + convert/sentencepiece_model.proto

  Responsibility: Reads SentencePiece tokenizers from any model.

  Atlas equivalent / missing: Atlas has nothing.

  ────────────────────────────────────────

  Ollama component: fs/ggml/, fs/gguf/

  File(s): fs/ggml/ggml.go (25k) + fs/gguf/

  Responsibility: Custom GGUF/GGML readers.

  Atlas equivalent / missing: Atlas has nothing.

  ────────────────────────────────────────

  Ollama component: llama/compat/ (C++ patch layer)

  File(s): llama/compat/ (1 file 170k LoC + patches)

  Responsibility: Translates old Ollama-published GGUFs to llama.cpp's expected

  metadata/tensor layout in-memory at load time.

  Atlas equivalent / missing: Atlas has nothing.

  ────────────────────────────────────────

  Ollama component: auth/auth.go (ed25519 SSH signing)

  File(s): auth/auth.go (85 lines)

  Responsibility: Signs requests to ollama.com with the user's local SSH key.

  Atlas equivalent / missing: Atlas has provider keys (sk-…/hf_…) but no

  client-side signing.

  ────────────────────────────────────────

  Ollama component: internal/cloud/policy.go

  File(s): internal/cloud/policy.go (566 bytes — tiny)

  Responsibility: A small but enforced policy module: "is cloud disabled? what's

  the disabled-operation error?" Every cloud passthrough consults it.

  Atlas equivalent / missing: Atlas has no cloud concept.

  ────────────────────────────────────────

  Ollama component: x/create/, x/transfer/, x/quant/, x/safetensors/

  File(s): x/ subpackages

  Responsibility: Separate executables for create, transfer, quant, safetensors.

  Atlas equivalent / missing: Atlas has no CLI subcommands beyond the single

  atlas script.

  What Atlas is currently missing vs Ollama

  1. No inference backend abstraction — LlamaServer interface in llm/server.go

     lets Ollama swap subprocess engines (llama.cpp ↔ MLX) without touching

     route handlers. Atlas has one httpx client with no seam to add a second

     backend.

  2. No scheduler — Ollama's Scheduler (1,460 lines) is the heart of

     multi-model, multi-GPU, OOM-recovery orchestration. Atlas has no concept of

     "loading a resource"; it only knows "rotating a key."

  3. No model store / no Modelfile / no template engine — Ollama's parser/,

     template/, convert/, tokenizer/, fs/, manifest/ collectively are ~30,000

     lines for "I own the model." Atlas owns nothing.

  4. No streaming parsers — Ollama's thinking/, tools/, harmony/ are real

     streaming parsers (500–1,500 lines each) that turn token streams into

     structured output. Atlas relies on upstream OpenRouter to deliver

     pre-parsed JSON, then re-emits it.

  5. No per-route middleware separation — Ollama's routes are route(middleware1,

     middleware2, ..., handler). The middleware does the inbound parse + body

     rewrite, the handler does the work, the response writer is also a

     middleware. Atlas inlines all of this into route handlers.

  6. No separate wire-format packages — Ollama's openai/ and anthropic/ are pure

     type definitions and one-way converters. middleware/openai.go is the gin

     glue. The boundary is explicit. Atlas's translation.py does all of this and

     is now 1,724 lines of mixed concerns.

  7. No first-class reverse-proxy subproject — Ollama's internal/proxy/ (Codex

     Desktop, Claude Desktop) is 3,200 lines of code, 6,000 lines of tests, with

     its own normalize, autoreview, errors, and models subsystems. Atlas's

     Codex support is ~250 lines bolted into routes.py.

  8. No capability detection — Ollama's Model.Capabilities() introspects GGUF

     metadata + chat template to determine if a model supports tools, thinking,

     vision, embeddings. Atlas has no concept of model capability.

  9. No tests — Ollama has ~70,000 lines of test code. Atlas has zero.

  10. No CLI subcommands — Ollama's cmd/ registers pull, push, create, run,

      show, list, delete, ps, cp, signin, signout, stop, serve, launch, plus an

      interactive TUI menu and an agent TUI. Atlas's CLI is one atlas script

      with start/stop/restart/status.

  11. No GPU/accelerator discovery — Ollama's discover/ enumerates CUDA, ROCm,

      Metal, Vulkan, sets VRAM tiers, etc. Atlas has none of this.

  12. No auth/signing module — auth/auth.go + server/auth.go is a real ed25519

      SSH-signing flow for ollama.com. Atlas has nothing analogous (and probably

      doesn't need one, but the structural separation is worth noting).

  13. No cloud policy module — internal/cloud/policy.go is 566 bytes, but every

      cloud code path in Ollama consults it. Atlas has no equivalent "should I

      forward to a remote upstream?" decision point.

  Architectural patterns Atlas could learn from

  1. Split translation.py along wire-format lines. openai.py and anthropic.py

     should be separate packages, with one-way converter functions (FromXRequest

     → api.ChatRequest, api.ChatResponse → ToXStreamChunks). The translation

     should be testable without HTTP.

  2. Add a Server interface like LlamaServer. Atlas's ProxyCore is a concrete

     class with no seam. A Backend interface (Complete, Chat, Embed) would let

     Atlas add a second backend (e.g. a local llama.cpp subprocess) without

     changing route handlers.

  3. Move wire-format translation into middleware. Atlas's ChatMiddleware() /

     AnthropicMessagesMiddleware() equivalent would (a) parse the inbound body

     to a wire-format type, (b) convert to the internal type, (c) rewrite

     c.Request.Body, (d) wrap c.Writer in a translator that converts the

     outbound chunks. Route handlers would then only deal with the internal

     type.

  4. Add a Scheduler-like module even without local models. The pattern of

     "request → pick resource → load if needed → bound concurrency →

     mark_success/mark_error" applies to API keys. Atlas's KeyPool is the start

     of this; it should live in its own package with an interface.

  5. Tests. Ollama ships ~70k lines of test code. Atlas has none. The biggest

     single piece of architectural value Ollama has that Atlas doesn't is

     confidence that the thing works.

  6. Per-route logging middleware. Atlas's withInferenceRequestLogging analog

     would be a requestLogMiddleware that captures request bodies, generates

     replay curl, and writes to a tempdir. Currently Atlas's prettylog.py is

     good for the live terminal but the debug request body capture lives

     nowhere.

  7. A internal/proxy/ subdirectory for client-specific adapters. Atlas's Codex

     custom-tool logic is buried in routes.py. Ollama's

     internal/proxy/codex_desktop.go is a self-contained 690-line file that owns

     everything Codex-specific — including its own normalize step, error

     taxonomy, and routing catalog.

  8. Provider config as a value object with capabilities, not a tuple. Atlas's

     ProviderConfig is {name, base_url, key_prefix, default_model, key_file, 

     dead_keys_file, key_label}. Ollama's Model is {Config, Template, 

     Capabilities, GenerationDefaults, Messages, …}. If Atlas ever grew

     model-level awareness (e.g. "this provider supports tool calls, that one

     doesn't"), the Ollama shape is the one to follow.
