  atlas_proxy — full breakdown

  An LLM proxy that sits between Claude Code / Hermes (or any
  OpenAI/Anthropic-shaped client) and upstream providers (OpenRouter or
  HuggingFace). Solves key exhaustion via rotation, provider switching without
  restart, and protocol translation between OpenAI ↔ Anthropic ↔ OpenAI
  Responses.

  Layout (~6,150 lines of Python)

  atlas_proxy/
  ├── proxy/                  # 9 modules, 6,149 lines
  │   ├── config.py           (752) — env-driven settings, ProviderConfig
  registry, key lifecycle
  │   ├── proxy.py            (1119) — ProxyCore: HTTP forward, SSE streaming,
  retries, mid-stream errors
  │   ├── routes.py           (904) — FastAPI handlers: /v1/chat/completions,
  /v1/messages, /v1/responses
  │   ├── translation.py      (1724) — OpenAI↔Anthropic protocol translation,
  reasoning/thinking, tool adaptation
  │   ├── prettylog.py        (629) — production-grade request lifecycle logging
  (TTFT, chunks, usage)
  │   ├── keypool.py          (454) — lock-free key pool, partial-sticky +
  full-sticky modes, cooldown
  │   ├── main.py             (268) — FastAPI app, lifespan, periodic key reload
  │   ├── system_prompt.py    (143) — additive system prompt override injection

  Core components

  Provider switching — ProviderConfig dataclass centralizes base URL, key
  prefix, default model, key file paths. Active provider read from
  data/proxy_data/runtime_provider.json at import time (written by atlas restart
  --huggingface). Per-provider force-override flags
  (FORCE_DEFAULT_MODEL_OR/_HF).

  Key pool (keypool.py) — two modes:
  - partial_sticky (OpenRouter): round-robin among healthy keys, sticky until
    MAX_CONCURRENT_PER_KEY=24 or STICKY_MAX_USES=18 reached
  - full_sticky (HuggingFace): pins one key until explicitly retired

  State machine: HEALTHY → COOLING (exponential backoff: 45s × 2^n, capped at
  300s) → SUSPENDED (10min after 8 consecutive errors). HF: retire_key()
  permanently retires + writes to dead_hf_keys.txt + removes from active file.
  Reload preserves state by key string (not index).

  ProxyCore (proxy.py, 1119 lines) — the hot path. Single authoritative
  _enforce_default_model() overrides client-supplied model at the upstream
  boundary. Retry loop (max 5) with fast-fail when all keys unhealthy.
  Free-model semaphore caps concurrent streams at 25 (Nvidia worker limit). SSE
  streaming with:
  - Mid-stream error classification (structural, not substring):
    rate_limit/concurrency/idle_timeout/overloaded/context_length/generic_error
  - HF: permanent retirement on 402 / 429 / quota markers
  - Synthesized message_stop for Anthropic-format streams to prevent Claude Code
    hanging in "Thought for…"
  - data: [DONE] drop, SSE keepalives every 15s
  - Response-size cap (defaults to unlimited, ATLAS_MAX_RESPONSE_BYTES)

  Routes (routes.py, 904 lines) — three endpoints, both /v1/... and unprefixed
  aliases:
  - POST /v1/chat/completions — pure passthrough after prepare_chat_body()
  - POST /v1/messages — Anthropic format. For HF provider, converts response
    OpenAI→Anthropic (non-streaming + SSE)
  - POST /v1/responses — translates OpenAI Responses API → chat/completions SSE
    with proper response.created/output_item.added/content_part.added/output_tex
    t.delta/.done/response.completed events. Handles Codex custom_tool_call +
    apply_patch tools with {"input": "..."} JSON wrapper for round-trip
    preservation
  - GET /v1/models — returns Anthropic-shaped model IDs (claude-opus-5,
    claude-sonnet-5, claude-haiku-4-5, plus the active provider default) so
    Claude Code UI accepts them
  - GET /health, /health/keys, /stats (legacy CLI compat)

  Translation (translation.py, 1724 lines — the biggest module) — bidirectional
  OpenAI↔Anthropic with extensive normalization:
  - Tool format: Anthropic {name, description, input_schema} ↔ OpenAI {type: 
    function, function: {name, description, parameters}}. Codex custom/freeform
    tools adapted to a generic single-string input field
  - tool_choice conversion both directions (preserves disable_parallel_tool_use)
  - Message conversion: handles text blocks, tool_use/tool_result, images
    (base64+url), thinking blocks, redacted_thinking, server_tool_use,
    mcp_tool_use
  - Reasoning/thinking: collects every alias (reasoning, reasoning_effort,
    thinking, budget_tokens, include_reasoning, verbosity, output_config.effort)
    into a unified internal form, then emits the right shape per path
  - Context window safety: _enforce_input_limit() strips thinking blocks
    (internal monologue) and trims oldest messages when total >
    MAX_INPUT_TOKENS=180K. Prevents 400s from Claude Code's 1M token assumption
    exceeding backing model's ~200K window
  - Cache control preserved on round-trip via private _anthropic_cache_control
    keys (stripped before upstream send)

  System prompt override — additive, non-destructive. Prepends override as first
  system message (highest primacy), keeps all existing system content. Two
  modes: full additive, or STRIP_HARNESS mode that keeps only the billing-header
  block. Hot-reload on file mtime change every 5s.

  Logging (prettylog.py) — pretty terminal-first formatter (HH:MM:SS, colored
  level, short rid, key redaction), rotating file mirror (10MB × 3), per-request
  RequestTrace lifecycle (start → sent → upstream → TTFT → chunks → usage →
  finish), key-pool health rendering with degraded-state detection. Thresholds
  via env: TTFT_GOOD_MS=1500 / TTFT_BAD_MS=4000, TOTAL_GOOD_S=10 /
  TOTAL_BAD_S=30, TPS_GOOD=100 / TPS_BAD=30.

  CLI (atlas/bin/atlas) — repo-location-agnostic (walks up from script
  location). Subcommands: install / uninstall / start / stop / restart / status
  / logs / doctor / check / config / version. Fuzzy-matched (atlas srt →
  restart). Self-bootstraps rich into the repo-local venv on first run. Symlinks
  to /usr/local/bin/atlas (or atlas2 with ATLAS_BIN_NAME to avoid collision).

  Installer (setup/install.sh) — generates systemd unit with paths baked from
  $REPO_ROOT. Refuses to clobber existing non-ours units (checks marker string).
  Same with CLI symlink. --user mode skips systemd. --check runs health
  diagnostics.

  Runner (run.sh) — resolves its own location, sources .env (without
  overriding), ensures repo-local venv, unsets PYTHONPATH to prevent shadowing,
  supports --bg/--stop/--status with pidfile.

  Notable design choices

  - Repo-location-agnostic everywhere — Path(__file__).resolve().parent.parent
    for all paths
  - Content-based key reload (not mtime) — survives rapid writes, partial
    writes, preserved timestamps
  - Startup key shuffle — random.shuffle() on key file before pool construction
    (replaces shuf for macOS compat)
  - Empty key list is non-fatal — pool starts empty, hot-loads when file appears
  - HF dead-key migration on startup — migrate_hf_active_keys() cleans up
    orphans from old retirement path
  - Anthropic stop_reason drop on stream errors — idle_timeout / overloaded
    never synthesize a misleading end_turn; only clean early close with content
    gets a fake message_stop
  - Response size cap at the response boundary (not stream) — non-streaming
    only, returns 413
  - FORCE_DEFAULT_MODEL is authoritative — runs at _enforce_default_model() on
    every outgoing payload regardless of endpoint/stream/provider
  - Private keys for round-trip metadata: _anthropic_cache_control,
    _anthropic_thinking_blocks — stripped before upstream via
    _strip_private_keys()

  What it is NOT

  - Not a load balancer across multiple upstreams in a single request (one
    provider per process)
  - No auth on the proxy itself — assumes trusted network
  - No request rate limiting (upstream keys do that, with cooldown)
  - No persistent state beyond key files + runtime_provider.json +
    prompt_override.txt + rotating log
  - Codex-specific tool handling only — no general MCP transport, no session
    management beyond what the client sends

  That's the whole thing.

  What Atlas is currently missing vs Ollama

  1. No inference backend abstraction — LlamaServer interface in llm/server.go
     lets Ollama swap subprocess engines (llama.cpp ↔ MLX) without touching
     route handlers. Atlas has one httpx client with no seam to add a second
     backend.
  2. No scheduler — Ollama's Scheduler (1,460 lines) is the heart of
     multi-model, multi-GPU, OOM-recovery orchestration. Atlas has no concept of
     "loading a resource"; it only knows "rotating a key."
  3. No model store / no Modelfile / no template engine — Ollama's parser/,
     template/, convert/, tokenizer/, fs/, manifest/ collectively are ~30,000
     lines for "I own the model." Atlas owns nothing.
  4. No streaming parsers — Ollama's thinking/, tools/, harmony/ are real
     streaming parsers (500–1,500 lines each) that turn token streams into
     structured output. Atlas relies on upstream OpenRouter to deliver
     pre-parsed JSON, then re-emits it.
  5. No per-route middleware separation — Ollama's routes are route(middleware1,
     middleware2, ..., handler). The middleware does the inbound parse + body
     rewrite, the handler does the work, the response writer is also a
     middleware. Atlas inlines all of this into route handlers.
  6. No separate wire-format packages — Ollama's openai/ and anthropic/ are pure
     type definitions and one-way converters. middleware/openai.go is the gin
     glue. The boundary is explicit. Atlas's translation.py does all of this and
     is now 1,724 lines of mixed concerns.
  7. No first-class reverse-proxy subproject — Ollama's internal/proxy/ (Codex
     Desktop, Claude Desktop) is 3,200 lines of code, 6,000 lines of tests, with
     its own normalize, autoreview, errors, and models subsystems. Atlas's
     Codex support is ~250 lines bolted into routes.py.
  8. No capability detection — Ollama's Model.Capabilities() introspects GGUF
     metadata + chat template to determine if a model supports tools, thinking,
     vision, embeddings. Atlas has no concept of model capability.
  9. No tests — Ollama has ~70,000 lines of test code. Atlas has zero.
  10. No CLI subcommands — Ollama's cmd/ registers pull, push, create, run,
      show, list, delete, ps, cp, signin, signout, stop, serve, launch, plus an
      interactive TUI menu and an agent TUI. Atlas's CLI is one atlas script
      with start/stop/restart/status.
  11. No GPU/accelerator discovery — Ollama's discover/ enumerates CUDA, ROCm,
      Metal, Vulkan, sets VRAM tiers, etc. Atlas has none of this.
  12. No auth/signing module — auth/auth.go + server/auth.go is a real ed25519
      SSH-signing flow for ollama.com. Atlas has nothing analogous (and probably
      doesn't need one, but the structural separation is worth noting).
  13. No cloud policy module — internal/cloud/policy.go is 566 bytes, but every
      cloud code path in Ollama consults it. Atlas has no equivalent "should I
      forward to a remote upstream?" decision point.

  Architectural patterns Atlas could learn from

  1. Split translation.py along wire-format lines. openai.py and anthropic.py
     should be separate packages, with one-way converter functions (FromXRequest
     → api.ChatRequest, api.ChatResponse → ToXStreamChunks). The translation
     should be testable without HTTP.
  2. Add a Server interface like LlamaServer. Atlas's ProxyCore is a concrete
     class with no seam. A Backend interface (Complete, Chat, Embed) would let
     Atlas add a second backend (e.g. a local llama.cpp subprocess) without
     changing route handlers.
  3. Move wire-format translation into middleware. Atlas's ChatMiddleware() /
     AnthropicMessagesMiddleware() equivalent would (a) parse the inbound body
     to a wire-format type, (b) convert to the internal type, (c) rewrite
     c.Request.Body, (d) wrap c.Writer in a translator that converts the
     outbound chunks. Route handlers would then only deal with the internal
     type.
  4. Add a Scheduler-like module even without local models. The pattern of
     "request → pick resource → load if needed → bound concurrency →
     mark_success/mark_error" applies to API keys. Atlas's KeyPool is the start
     of this; it should live in its own package with an interface.
  5. Tests. Ollama ships ~70k lines of test code. Atlas has none. The biggest
     single piece of architectural value Ollama has that Atlas doesn't is
     confidence that the thing works.
  6. Per-route logging middleware. Atlas's withInferenceRequestLogging analog
     would be a requestLogMiddleware that captures request bodies, generates
     replay curl, and writes to a tempdir. Currently Atlas's prettylog.py is
     good for the live terminal but the debug request body capture lives
     nowhere.
  7. A internal/proxy/ subdirectory for client-specific adapters. Atlas's Codex
     custom-tool logic is buried in routes.py. Ollama's
     internal/proxy/codex_desktop.go is a self-contained 690-line file that owns
     everything Codex-specific — including its own normalize step, error
     taxonomy, and routing catalog.
  8. Provider config as a value object with capabilities, not a tuple. Atlas's
     ProviderConfig is {name, base_url, key_prefix, default_model, key_file, 
     dead_keys_file, key_label}. Ollama's Model is {Config, Template, 
     Capabilities, GenerationDefaults, Messages, …}. If Atlas ever grew
     model-level awareness (e.g. "this provider supports tool calls, that one
     doesn't"), the Ollama shape is the one to follow.
